# Project facts for the agent commands

The commands in `.agents/commands/` work in any project because they never name a path of their own. When one needs to know where your bug list is, how to run your tests or what counts as a deliberate workaround, it reads the matching bullet below.

Keep each bullet on one line, and keep the bold name at the start exactly as it is: commands find a bullet by searching for its name. A bullet that still has angle brackets has not been filled in. When a command meets one, it stops and asks you. `/setup-project-facts` fills this file in by reading the repo and asking you about anything it can't find.

- **Checks and tests**: after a change, run `fvm flutter analyze` and `fvm flutter test` (also listed under "After making changes" in `AGENTS.md`; CI runs both). No schema or generated-code check. A change to behaviour adds a changelog line with `bash scripts/add_changelog_line.sh "<line>"`. Never read `CHANGELOG.md`.
- **Records**: open bugs go in `BUGS.md`, deferred work in `TODO.md`, tasks only a human can do in `MANUAL_TODO.md`, fixes in `CHANGELOG.md` (write-only, through `scripts/add_changelog_line.sh`). The `record-keeping` skill has the rules. `/find-bandaids` parks the findings it keeps or defers under a `# Bandaids` heading in `TODO.md`. Public bug reports from users arrive as GitHub issues (dev-cetera/dbscope); those stay on GitHub.
- **Audit records**: each audit command keeps its findings in `todo/<topic>.md`, for example `/find-exploits` → `todo/exploits.md`, `/find-dead-code` → `todo/dead_code.md`, `/find-stale-references` → `todo/stale_references.md`. The rules are in `todo/AGENTS.md`. A re-run checks the open entries again first. Missing files are created on the first run.
- **Readability and comments**: readable code is defined by `lib/AGENTS.md`, `.agents/rules/dart-discipline.md` and the lints in `analysis_options.yaml` (flutter_lints). Comment rules: comments explain why, not what; every test file opens with a comment stating the contract it pins down (`test/AGENTS.md`).
- **UI and business code**: UI lives in the feature folders' `*_view.dart` / `*_tab_view.dart` files and `lib/shell/`, shared state in `lib/shell/app_state.dart` (`AppState`) and `lib/connection/registry.dart` (`ConnectionRegistry`), pure business rules in `lib/meta/` (no Flutter), `lib/util/sql_quote.dart`, `lib/util/sql_parse.dart`, `lib/db/dml.dart` and `lib/query/pager.dart`, shared widgets in `packages/widgets/` (barrel `package:widgets/widgets.dart`), analyze command `fvm flutter analyze`.
- **Security**: there is no app login; database credentials are the auth. Passwords and AI keys live in the OS keychain via `lib/connection/secure_store.dart`; portable links are AES-GCM encrypted in `lib/connection/connection_link.dart`; SQL safety invariants and read-only fencing are in `docs/architecture.md` ("SQL safety invariants") and enforced in `lib/util/sql_quote.dart`, `lib/db/dml.dart` and `executeReadOnly`; metadata access control choke points are listed under "Schema metadata" in `docs/architecture.md`. The web build's `packages/dbscope_pg_proxy` is the only network-facing server. Dev-only bypass switch: none. Reporting: `SECURITY.md`.
- **Compliance**: dbscope collects no user data and has no backend of its own: no accounts, no analytics, no telemetry. Data leaves the machine only to the user's own databases and, when the user configures a key, to the AI provider they chose (`lib/ai/`). No privacy policy or terms beyond `LICENSE`; questions that need a lawyer go to `MANUAL_TODO.md`.
- **Marketing site and SEO**: site source `site/index.html` (one static page, deployed by `.github/workflows/pages.yml` to https://dev-cetera.github.io/dbscope/), routes: just `/`, page head and meta tags in `site/index.html`, social card `site/assets/og.svg` → `og.png`, no sitemap or robots file, brand voice: plain, honest, "vibe coded and open source" (see `README.md`).
- **Production readiness**: no separate checklist; release scope is the `README.md` feature list, the release runbook is "Releasing" in `README.md` and `.github/workflows/release.yml`, and the gates are `fvm flutter analyze`, `fvm flutter test` and a green Release run (signed + notarized when the Apple secrets are set).
- **Search helpers**: symbol finder `bash scripts/agent/info_find.sh SYMBOL` (Dart-aware alternative `bash .agents/skills/dart-search/scripts/info_find.sh SYMBOL`), capped search `bash scripts/agent/info_grep.sh PATTERN PATH`, doc drift `bash scripts/agent/info_doc_drift.sh`. The shell is bash.
- **Product brief**: a free, open-source desktop database GUI for developers who work with Postgres and SQLite (including SQLite inside mobile apps), built to stay fast on huge tables; `README.md` is the brief. Words with a special meaning here (host window, Server, executor, profile, connection link, metadata, selector) are defined in `docs/architecture.md`.
- **Deliberate workarounds, never flagged as band-aids**: macOS App Sandbox disabled in `macos/Runner/*.entitlements` (needs to shell out to adb/xcrun/gcloud/cloud-sql-proxy); `usesDataProtectionKeychain: false` in `lib/connection/secure_store.dart` (avoids keychain-access-groups entitlement on unsigned builds); `TableTabView` 50 000-row buffer with 5 000-row trims; Query tabs capped at 10 000 rows; two independent executors per Postgres profile (server-side `ConnectionService` and per-window `ConnectionRegistry`); `WindowRouter` owns the single `desktop_multi_window` method handler; `desktop_multi_window` still via CocoaPods.
- **Deliberately unused, never flagged as dead code**: `test/widget_test.dart` (intentional placeholder); `TableListStep` in `lib/navigator/` (kept as the explicit column-0 model, never constructed); the commented-out Doom and Warcraft theme dependencies in `pubspec.yaml`.
- **Who uses shared code**: `packages/widgets`, `packages/data_grid` and `packages/schema_viewer` are used by the app in `lib/` and by the theme/backend plugin packages in `packages/dbscope_*_plugin`; `packages/app_data_explorer` is used by `packages/dbscope_sqflite_plugin`. A symbol there is dead only when none of them reference it.
- **Endpoints**: in-process RPC, not HTTP. One endpoint is a `server.onRequest('<method>', ...)` handler in `lib/server/services/*.dart`, registered with the `Server` in `lib/server/server.dart`, with a thin client wrapper in `lib/rpc/services/`. The web proxy's WebSocket protocol lives in `packages/dbscope_pg_proxy/bin/`.
- **Patterns**: no pattern catalogue yet; `/unify-patterns` creates `docs/patterns.md` on first run, and a sanctioned exception is marked `// pattern-exception: <reason>`.
- **Agent prompts**: commands live in `.agents/commands/`, skills in `.agents/skills/`, rules in `.agents/rules/`. Folder guides are the `AGENTS.md` files listed under "Folder guides" in the root `AGENTS.md`. After editing a command, run none (they are markdown; re-running an installer overwrites `.agents/commands/`, so put project specifics here instead).
- **Prompts**: AI prompts the product itself sends are in `lib/ai/sql_assistant.dart` and `lib/ai/field_explainer.dart` (providers via `package:ai_broker`), and are tested by hand against a real database; there is no prompt test harness.
- **DNS**: no custom domains; the site is on dev-cetera.github.io and the web app on dbscope-prod.web.app (Firebase Hosting, `firebase.json`).
- **Sentry**: not used.
- **Core docs**: `AGENTS.md` (agent workflow; must match the scripts and folder guides that exist), `docs/architecture.md` (must match `lib/`, `packages/` and `.github/workflows/`), `README.md` (must match shipped features, platforms and release asset names), `CONTRIBUTING.md` (must match the real setup and check commands).
- **Dart packages**: the packages are `.` (the app) and every folder under `packages/`; the style rules are in `.agents/rules/dart-discipline.md` plus `analysis_options.yaml`; generated files are `lib/firebase_options.dart` and `**/*.g.dart`; out of scope: `build/`, `.dart_tool/`, `macos/Pods/`, `macos/Flutter/`.
- **Session transcripts**: Claude Code keeps them in `~/.claude/projects/-Users-robmllze-Projects-flutter-dev-cetera-dbscope/*.jsonl` (and `...-compledo-frontend-dbscope` for the submodule clone). Codex keeps them in `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`.
